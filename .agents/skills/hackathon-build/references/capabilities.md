# Capabilities and sources

## One workflow owner

The coordinator owns scope, time, requirements, assignments, integration, and demo readiness. Beryl owns canonical repository context and selected deterministic checks. The UI/UX owner selects the design and frontend implementation workflow under [UI/UX ownership](ui-ux.md). Superpowers or ECC supplies the shared planning and other engineering workflows through the required routing below. Other specialists can supplement those engineering tasks when relevant. Do not assume feature parity or the presence of any plugin.

There is one canonical scope, build plan, set of ticket specifications, and approval record. Avoid stacking separate planning loops. User instructions and authorization remain authoritative and do not imply unrelated publication, installation, or messaging permissions.

## Required engineering workflow routing

Apply this gate before creating or materially revising the shared implementation plan and before each teammate starts engineering work outside the owner-selected UI route. UI-specific design/frontend plans, implementation, and verification follow [UI/UX ownership](ui-ux.md) instead; this is not a fallback. In mixed tickets, apply the gate to backend, API/schema, and shared integration logic separately. Recheck when the agent environment changes. A coordinator's installed skills do not establish what is available on a teammate's laptop.

1. Discover the current agent's exposed skills and relevant project/local installations. Inspect actual Superpowers and ECC instructions for this phase; a downloaded repository, remembered skill name, or a ticket's suggestion does not establish an available workflow. A usable workflow has readable instructions and its required steps can be performed with available tools and authorization. If the native invocation mechanism is absent but the instructions can be followed faithfully, read and follow them directly and record that execution method.
2. When a relevant usable Superpowers or ECC workflow exists, you MUST use one. Honor the user's provider choice when usable; otherwise retain a suitable recorded choice or choose the best phase fit and state why. When both exist, select one primary workflow for that phase instead of combining competing planning systems. For example, inspect an installed Superpowers planning skill for planning, or discover ECC's actual planning capability; for implementation inspect execution, TDD, and verification instructions. Names and dependencies must come from the installed version. Follow required supporting skills and gates, including red–green–refactor when its instructions require TDD. Merely naming a skill or adopting its document headings is not using it.
3. Before doing the phase's work, announce the provider, exact workflow name(s), and native invocation or direct instruction-following method. Record **phase; provider; exact skill/source locator and revision if available; execution method; selection reason; status** in the canonical build plan for planning, or the teammate's ticket/handoff for implementation. Initial status is selected; completion adds the steps and verification evidence actually performed. Never label selection alone as compliance.
4. If neither provider has a usable workflow for the phase, announce **“Fallback — [phase]: [reason]. Using the coordinator's portable procedure.”** before proceeding. Record the discovery outcome, missing or incompatible capability, replacement procedure, and affected verification limits in the same artifact. Check the other provider before falling back. An unreadable skill, unavailable required tool, or incompatible gate must be named; prefer another usable installed workflow to changing an upstream workflow. A readable workflow without a native slash command is not automatically unavailable.

Fallback uses the planning guidance in [Ideation](ideation.md), [Bootstrap](bootstrap.md), and [Team tickets](team.md), or the implementation and verification guidance in [Execution](execution.md), together with actual repository conventions and checks. Keep required tests and acceptance evidence. If a requirement cannot be verified, record it as blocked or unverified rather than completed. For partial coverage, apply the gate separately to execution, testing, and verification: use each relevant usable installed workflow for the part it covers and disclose fallback only for uncovered parts. For example, a usable TDD skill MUST still be used when execution and verification need portable procedures; it does not prove an execution or review workflow was followed.

Time pressure, a short ticket, and existing repo conventions do not justify bypassing a usable installed workflow. If the user explicitly overrides routing, honor that instruction and record **Fallback — user-directed override**, what was skipped, and the replacement procedure. If a selected workflow becomes unusable mid-task, disclose the transition and reapply this gate. Any adapted upstream procedure is a disclosed fallback with differences, never a claim of strict compliance. Do not install dependencies or plugins automatically to satisfy routing.

Portable repository docs work without a globally installed skill. For skill discovery use a project-local copy of this complete folder under `.agents/skills/hackathon-build` for Codex, `.claude/skills/hackathon-build` for Claude Code, or `.cursor/skills/hackathon-build` for Cursor. The repo installer performs these copies without overwriting an existing different skill. Explicitly asking an agent to read `SKILL.md` is the fallback when discovery differs by version. Installation does not configure hooks, authentication, or automatic cross-machine execution.

Official capability references: [Codex](https://developers.openai.com/codex/skills), [Claude Code](https://code.claude.com/docs/en/skills), [Cursor](https://cursor.com/docs/skills). Verify current docs when adapting tool-specific behavior.
