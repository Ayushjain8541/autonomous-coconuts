# P3 — Existing ML workflow merged with the team bootstrap

The local ML commits have been merged with the shared main history. Development
and inference remain separate in `development/` and `prediction/`. Existing
backend, UI, logical adapters, shared contracts, and fixture tests are preserved.

## Delivered behavior

- `prediction/predict.py` loads the tracked XGBoost model and encoding metadata;
  it preserves input rows and telemetry, generates `risk = log10(Pc)`, and adds
  `class_model` with Safe, Elevated risk, or Critical.
- All twelve source features are declared in `prediction/predict.py` and the
  model's `feature_encoder.json`. Numeric NaNs use native missing-value branches;
  unseen object types have all-zero category indicators.
- Supplied `risk`, `max_risk_estimate`, and `max_risk_scaling` are removed before
  inference. Distances are metres, with Critical precedence under the prompt's
  thresholds. Missing/nonfinite classification distances fail explicitly.
- Training, evaluation, and notebook outputs stay in `development/artifacts/`.
  Reviewed model and encoder files can be copied into `prediction/artifacts/`.

## Target and integration boundary

This model estimates the risk associated with each telemetry row. It does not
implement the shared contract's final-report forecast from reports at least two
days before TCA. The latest-event CSV selects an available row; it is not a
final-risk forecast. Event IDs are included as requested by the local user.

The bootstrap's `ml/predictor.py` remains unavailable for real inference, and the
HTTP server's demo remains synthetic. No shared v1 adapter, UI/provider wiring,
or contract compatibility is claimed. P2/P3 must agree the target semantics and
adapter before connecting this model to encounter analysis.

```sh

development/.venv/bin/python -m pytest -q development/tests
development/.venv/bin/python development/execute_notebook.py
```

## CSV upload helper and teammate export

The user requested a reusable helper and teammate handoff, leaving the upload
screen and HTTP API to P1/P2. `prediction/predict.py` now exports:

- `predict_uploaded_csv(content)`: CSV bytes, text, or a readable upload stream
  to a scored pandas DataFrame, entirely in memory.
- `predict_dataframe(frame)`: the same operation on parsed telemetry without

## Judge-facing training and accuracy evidence

Branch: `p3/model-benchmarks`, based on merged main `887f0ae`.
The user requested a training explanation and a simple accuracy comparison in
the root README. `development/benchmark_predictions.py` now evaluates the frozen
CSV against supplied same-row reference labels, without deserializing, training,
tuning, or invoking the prediction model. This post-hoc reference-label use is
separate from the unchanged inference rule that drops all three forbidden fields.

Observed report-level tier agreement is 23,369/24,484 (95.45%). The distance-only
baseline is 23,368/24,484 (95.44%), so the tier metric is mostly distance-driven.
Numerical predictions are within one log10 unit in 18.84% of reports, and the
probability-only Critical recall is 39/233 (16.74%; 194 false negatives). These
figures do not establish calibrated probabilities or final-TCA forecasting.
The earlier grouped holdout numbers remain a separate evaluation protocol.

The root README explains XGBoost, feature handling, the event-separated split,
early stopping, refitting, exact metric definitions, baselines, and limitations.
It includes a presentation-ready explanation that does not advertise 95.45% as
probability accuracy. The benchmark report records aggregate metrics and hashes
under ignored `development/artifacts/`; raw input and prediction CSVs stay local.

This single change boundary contains `README.md`, `development/README.md`,
`development/benchmark_predictions.py`, its new test file,
